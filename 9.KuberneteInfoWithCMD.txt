WHAT IS KUBERNETES? 
Kubernetes (K8s) is an open-source container orchestration platform that automatically deploys, scales, and manages containerized applications across a cluster of servers.

                    ----KUBERNETES COMPREHENSIVE ARCHITECTURE & OBJECT REFERENCE----

1. CONTROL PLANE (THE MANAGEMENT OFFICE)
-----------------------------------------------------------------------------------------------------------------------------
* kube-apiserver              # 🏢 [Front Office]       | Accepts commands from users and components; coordinates all cluster activity.
* etcd                        # 📓 [Master Filing Room] | Distributed key-value database storing every piece of cluster state and history. (Like: CHEF OHAI VS ANSIBLE SETUP)
* kube-scheduler              # 🧠 [Placement Planner]  | Checks available node resources and decides where new Pods should run.
* kube-controller-manager     # 👮 [Quality Inspector]  | Continuously compares current cluster state with desired state to fix gaps.(actual state = desired)

2. WORKER NODE COMPONENTS (THE FACTORY FLOOR)
-----------------------------------------------------------------------------------------------------------------------------
* Kubelet                     # 🧑‍🔧 [On-Site Foreman]  | Listens to Control Plane; ensures assigned Pods remain healthy on the node.
* Kube-proxy                  # 🔀 [Network Dispatcher] | Configures network routing so traffic smoothly reaches the correct Pod IP.
* Container Engine            # ⚙️ [Power Engine]       | Low-level software (containerd/CRI-O) that pulls images and executes containers.

3. PODS & COMMON MULTI-CONTAINER FAILURES
-----------------------------------------------------------------------------------------------------------------------------
* Pod                         # 🏠 [Shared Living Space]| Smallest unit containing one or more closely tied containers sharing resources.
* Multi-Container Pod         # 👯 [Team Unit]          | Multiple containers in one Pod (e.g., Main App + Logging Sidecar) working together.
* Failure: Port Collision     # 🚪 [Traffic Bottleneck] | Fails when 2 containers inside the same Pod attempt to claim the same network port.
* Failure: Race Condition     # 🏁 [Timing Mismatch]    | Fails when the main container boots up before its helper container is ready.
* Failure: Resource Crash     # 🍕 [Memory Overload]    | Fails when 1 greedy container consumes all CPU/RAM, causing the entire Pod to crash.

4. HIGH-LEVEL OBJECTS & OPERATIONS (THE BLUEPRINTS)
-----------------------------------------------------------------------------------------------------------------------------
* Volume                      # 💾 [External Storage]   | Persistent drive mounted into Pods so data stays safe even if containers restart.
* ReplicaSet                  # 👯 [Copy Supervisor]    | Guarantees an exact count of identical Pod clones are active at all times.
* Deployment                  # 📋 [Release Manager]    | Handles software updates, scaling up/down, and automatic rollbacks smoothly.
* Service                     # 🚦 [Constant Endpoint]  | Gives a stable IP address and load balancer so apps can always be reached.

5. MANAGEMENT & SETUP TOOLS
-----------------------------------------------------------------------------------------------------------------------------
* kubectl                     # 📱 [Remote Controller]  | Command line interface used by admins to send commands to the API Server.
* kubeadm                     # 🧰 [Assembly Toolkit]   | Bootstrap utility used to quickly install and stand up a new Kubernetes cluster.
* kubefed                     # 🌐 [Global Director]    | High-level tool used to federate and manage multiple Kubernetes clusters at once.

🧊 Kubernetes Object: 
        A persistent blueprint/entity in your cluster that Kubernetes continually manages to match your desired state.
📂 YOUR FILE (Manifest) What You Want vs. What Kubernetes Does 📄 YOUR YAML FILE (The Object)
 ┌────────────────────────────────────────┐
 | kind: Pod                              |
 | metadata:                              |
 |   name: testpod                        |
 | spec:                                  |
 |   containers:                          |
 |     - name: c00                        |
 |       image: ubuntu                    |
 └────────────────────────────────────────┘
                    │
                    ▼ (You run: kubectl apply -f pod.yml)
 💾 KUBERNETES DATABASE (Saved as an Object)
 ┌────────────────────────────────────────┐
 | Stored Desired State (`spec`):         |
 | "I want 1 Pod named 'testpod' running."|
 └────────────────────────────────────────┘
                    │
                    ▼ (Kubernetes Control Loop constantly checks...)
 ⚡ CLUSTER REALITY (`status`)
 ┌────────────────────────────────────────┐
 | 🔍 Is the Pod running right now?       |
 | 🟩 YES -> Status: Running (All good!)  |
 | 🟥 NO  -> Status: Crashed/Deleted      |
 |           (Kubernetes automatically    |
 |            restarts it to fix it!)     |
 └────────────────────────────────────────┘

 ⚙️ Spec vs. Status:
   * 📋 spec   = Desired state (what you want the cluster to look like).
   * 🔍 status = Actual state (what is actually happening right now).
#
 🔀 Imperative vs. Declarative:
   * ⚡ Imperative  = Giving direct command-line instructions (e.g., kubectl run).
   * 📄 Declarative = Applying configuration files (e.g., kubectl apply -f file.yml).
#
 📦 Pod: The smallest deployable unit in Kubernetes containing one or more containers sharing the same network and storage.
#
 - 🔄 Restart Policy: Tells Kubernetes what to do when a container stops or crashes:
     * 🔄 Always    (Default) : Always restarts the container, no matter why it stopped. (Best for web servers like NGINX/Apache).
     * ⚠️ OnFailure           : Restarts ONLY if it crashes/errors (exit code ≠ 0). (Best for batch/backup jobs).
     * 🛑 Never             : Never restarts the container, even if it crashes. (Best for one-time scripts).

                                                    🏷️ 1. LABELS & SELECTORS OVERVIEW

💡 WHAT THEY ARE: 
Labels are like sticky notes attached to Kubernetes objects. Selectors are search filters used to find and manage objects based on those labels.

🖼️ VISUAL CONCEPT:
🏷️ PODS WITH LABELS                                        🔍 SELECTOR (The Filter)
 ┌─────────────────────────┐                                ┌─────────────────────────┐
 │ Pod 1 (env: development)│                                │                         │
 │ Pod 2 (env: production) │ ──(Find)──────────────────────>│ "Give me all pods       │
 │ Pod 3 (env: development)│                                │  where env=development" │
 └─────────────────────────┘                                └────────────┬────────────┘
                                                                         │
                                                                         ▼ 🎯 Matches: Pod 1 & Pod 3

⚡ IMPERATIVE COMMANDS (CLI):
kubectl label pod delhipod env=development                                                  # 🏷️ Adds a label to a running pod
kubectl get pods --show-labels                                                              # 📊 Displays all pods with their labels
kubectl get pods -l env=development                                                         # 🔍 Filters pods using an equality selector

📄 DECLARATIVE YAML EXAMPLE (pod.yaml):
kind: Pod
apiVersion: v1
metadata:
  name: delhipod
  labels:
    env: development
    class: pods
spec:
  containers:
    - name: c00
      image: ubuntu
      command: ["/bin/bash", "-c", "while true; do echo Hello-Bhupinder; sleep 5 ; done"]

                                                    🔍 2. SELECTOR TYPES & REFERENCE TABLE

Equality-Based Selector: Matches exact values using operators like `=`, `==`, or `!=`. (Example: `env = development` or `environment != production`)
Set-Based Selector: Matches against a group or set of values using `In`, `NotIn`, or `Exists`. (Example: `myname In (Bhupinder, Bupinder, Bhopendra)`)

+---------------------+-------------------+-------------------------------------------------------------+---------------------------------------+
| SELECTOR TYPE       | OPERATOR          | DESCRIPTION                                                 | KUBECTL COMMAND EXAMPLE               |
+---------------------+-------------------+-------------------------------------------------------------+---------------------------------------+
| Equality-Based      | =  or  ==         | Matches exact values                                        | kubectl get pods -l env=dev           |
| Equality-Based      | !=                | Matches anything except the specified value                 | kubectl get pods -l env!=prod         |
| Set-Based           | in                | Matches if the label value is inside a specific list        | kubectl get pods -l 'name in (A, B)'  |
| Set-Based           | notin             | Matches if the label value is NOT in the list               | kubectl get pods -l 'env notin (prod)'|
| Set-Based           | Key Exists        | Matches if the label key simply exists (any value)          | kubectl get pods -l 'hardware'        |
+---------------------+-------------------+-------------------------------------------------------------+---------------------------------------+

                                                    🖥️ 3. NODE SELECTOR

💡 WHAT IT IS: 
Forces Kubernetes to place a Pod only onto a specific cluster node that matches required hardware or environment labels.

📄 DECLARATIVE YAML EXAMPLE (nodeselector.yaml):
kind: Pod
apiVersion: v1
metadata:
  name: nodelabels
  labels:
    env: development
spec:
  containers:
    - name: c00
      image: ubuntu
      command: ["/bin/bash", "-c", "while true; do echo Hello-Bhupinder; sleep 5 ; done"]
  nodeSelector:
    hardware: t2-medium

                                                    🚀 4. SCALING, RELIABILITY, & CONTROLLERS

📌 WHY CONTROLLERS ARE REQUIRED:
Kubernetes does not keep apps running or scaled up automatically by default. We use Controller objects (like ReplicationController, ReplicaSet, Deployment, HPA) to provide:
📈 Scaling: Instantly adjusting replica counts up or down based on load.
🛡️ Reliability (Self-Healing): Automatically recreating crashed or failed pods.
🌐 Load Balancing: Spreading incoming user traffic evenly across instances.
🔄 Rolling Updates: Updating app versions seamlessly with zero downtime.

🖼️ VISUAL CONCEPT (SELF-HEALING & SCALING):
🎛️ REPLICA SET CONTROLLER
 ┌─────────────────────────────────────────────────────────────────┐
 │ 🔄 Continuously monitors cluster to match desired replica count │
 └─────────────────────────────────┬───────────────────────────────┘
                                   │
             ┌─────────────────────┴─────────────────────┐
             ▼ (If a pod crashes 💥)                     ▼ (If you scale up 📈)
 ┌───────────────────┐                       ┌───────────────────┐
 │ 💥 Pod 1 (Dead)   │                       │ ➕ Spawns Pod 3   │
 │ 🟢 Pod 2 (Running)│                       │    automatically  │
 └─────────┬─────────┘                       └───────────────────┘
           │
           ▼ (Automatically recreates!)
 ┌───────────────────┐
 │ 🟢 Pod 1 (New)    │
 │ 🟢 Pod 2 (Running)│
 └───────────────────┘

📊 SCALING ARCHITECTURE (HOTSTAR IPL CASE STUDY):
 📈 MANUAL SCALING (PRE-MATCH PREPARATION)
 ┌──────────────────────────┐               ┌──────────────────────────┐
 | 100 Replicas (Normal)    | ──(Scale)──>  | 5,000 Replicas (IPL Peak)|
 └──────────────────────────┘               └──────────────────────────┘

 🤖 AUTOMATIC AUTO-SCALING (HPA - LIVE TRAFFIC SPIKES)
 ┌──────────────────────────┐               ┌──────────────────────────┐
 | CPU Usage > 70%          | ──(Triggers)─>| Auto-scales dynamically  |
 |                          |               | from 100 to 10,000 Pods  |
 └──────────────────────────┘               └──────────────────────────┘

⚡ 1. MANUAL SCALING (PREDICTABLE TRAFFIC SURGES)
kubectl scale deployment hotstar-ipl-stream --replicas=5000                                 # 🚀 Pre-warms streaming service to 5,000 pods before match starts
kubectl scale deployment hotstar-ipl-stream --replicas=100                                  # 📉 Cools down infrastructure to baseline capacity after match

🤖 2. AUTOMATIC SCALING (HORIZONTAL POD AUTOSCALER - HPA)
kubectl autoscale deployment hotstar-ipl-stream --cpu-percent=70 --min=100 --max=10000     # 📈 Automatically adjusts replica count when average CPU usage exceeds 70%
kubectl get hpa hotstar-ipl-stream                                                          # 📊 Displays active replica count, target metrics, and current usage

📄 DECLARATIVE HPA MANIFEST (hpa.yaml):
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: hotstar-ipl-hpa
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: hotstar-ipl-stream
  minReplicas: 100
  maxReplicas: 10000
  metrics:
  - type: Resource
    resource:
      name: cpu
      target:
        type: Utilization
        averageUtilization: 70

🌟 WHAT IS A KUBERNETES REPLICA SET?
While a basic ReplicationController only uses simple equality checks, a modern ReplicaSet provides advanced pod management:
🛡️ Self-Healing: Automatically recreates crashed or deleted pods to maintain the exact desired replica count.
🎯 Advanced Selectors: Supports powerful set-based expressions (In, NotIn, Exists) for flexible pod grouping.
⚖️ Scalability: Instantly scales pod replicas up or down to handle changing workloads.

📋 WHAT IS A KUBERNETES REPLICATION CONTROLLER?
As the legacy precursor to modern ReplicaSets, a ReplicationController provides foundational cluster scaling:
🔢 Exact Replica Guarantees: Ensures a specified exact number of pod copies are running at all times.
🔍 Equality-Based Filtering: Uses basic key-value match filters (e.g., env=dev) to target and manage pods.
🛡️ Basic Self-Healing: Recreates pods if nodes fail or containers crash, though now largely superseded by ReplicaSets and Deployments.

📦 WHAT IS A KUBERNETES DEPLOYMENT?
While a ReplicaSet only manages pod counts, a Deployment sits at the top level and gives you application lifecycle superpowers:
🔄 Rolling Updates (Zero Downtime): Updates pods one by one without dropping user connections.
⏪ Easy Rollbacks: Instantly roll back to previous stable versions if a bug is introduced.

 🗂️ DEPLOYMENT & CLUSTERIP SERVICE (INTERNAL VIRTUAL IP ROUTING)
 • What is happening: We create a Deployment with an Apache container, paired with a **ClusterIP** service. Because individual pods are ephemeral (when a pod is destroyed, its IP address is gone forever), Kubernetes allocates a stable **Virtual IP (VIP)** via ClusterIP so other components inside the cluster can always reliably reach the application.

 • Updated Manifest Section (`clusterip-deployment.yaml`):
   apiVersion: apps/v1            # ⚙️ API version for deployment workloads
   kind: Deployment               # 🏷️ Object type: Deployment
   metadata:
      name: mydeployments         # 🏷️ Name of the deployment controller
   spec:
      replicas: 1                 # 🔢 Desired count of pod replicas
      selector:                   # 🎯 Tells the controller which pods to watch/belong to
       matchLabels:
        name: deployment          # 🔍 Label selector to target pods
      template:                   # 📋 Blueprint for creating new pods
        metadata:
          name: testpod1          # 🏷️ Pod template name
          labels:
            name: deployment      # 🏷️ Label assigned to pods managed by this deployment
        spec:
         containers:
           - name: c00            # 🐳 Container name inside deployment pod
             image: httpd         # 🖼️ Apache web server image
             ports:
               - containerPort: 80# 🔌 Exposes container port 80
   ---
   kind: Service                  # 🏷️ Object type: Service
   apiVersion: v1                 # ⚙️ API version for core objects
   metadata:
     name: demoservice            # 🏷️ Name of the internal cluster service
   spec:
     ports:
       - port: 80                 # 🔌 Service port exposed on the Virtual IP
         targetPort: 80           # 🎯 Target container port inside the pod
     selector:
       name: deployment           # 🔍 Apply this service to any pods matching this label
     type: ClusterIP              # 🌐 Internal Virtual IP (ClusterIP) service type

 🛠️ Commands Executed & Output Logs:

🩺 HEALTHCHECK LABS - LIVENESS PROBE
• What is happening: We configure a Liveness Probe using an `exec` command to check the health status of a container by checking if a file (`/tmp/healthy`) exists. If the command fails, Kubernetes will automatically restart the container.

• Updated Manifest Section (`liveness-probe.yaml`):
   apiVersion: v1                     # ⚙️ API version for core objects
   kind: Pod                          # 🏷️ Object type: Pod
   metadata:
     labels:
       test: liveness                 # 🏷️ Label identifier for test pods
     name: mylivenessprobe            # 🏷️ Name of the liveness probe pod
   spec:
     containers:
       - name: liveness               # 🐳 Container name
         image: ubuntu                # 🖼️ Ubuntu base image
         args:
           - /bin/sh
           - -c
           - touch /tmp/healthy; sleep 1000 # ⏳ Creates health file on start and keeps running
         livenessProbe:               # 🔍 Healthcheck configuration block
           exec:
             command:
               - cat                  # 🛠️ Command to run inside container
               - /tmp/healthy         # 📄 Target file path being checked
           initialDelaySeconds: 5     # ⏱️ Wait 5 seconds before running the probe for the first time
           periodSeconds: 5           # 🔄 Run the probe every 5 seconds thereafter
           timeoutSeconds: 30         # ⏳ Maximum seconds to wait for the probe command to finish

🛠️ Commands Executed & Output Logs:
   kubectl apply -f liveness-probe.yaml
   # -> Expected Output: pod/mylivenessprobe created
   
   kubectl describe pod mylivenessprobe
   # -> Expected Output: Inspect events and container restart count under Liveness probe status

⚠️ Liveness Probe Fail Case
Infinite Restart Loop (`CrashLoopBackOff`): If the health file is accidentally deleted (e.g., via `rm /tmp/healthy`) or the application becomes unresponsive, the probe command will exit with a non-zero status code. Kubernetes will repeatedly kill and restart the container, leading to service disruption.

## 1. 🛑 RESOURCE QUOTAS & DEFAULT RANGES
### 📌 Definition
* **Resource Quota:** A cluster-level object used to restrict aggregate resource consumption (CPU, memory, storage, and pod counts) per namespace.
* **Default Range (LimitRange):** A mechanism that enforces default resource request and limit values for containers running inside a namespace if the container's YAML manifest omits resource definitions.

## 2. 📈 HORIZONTAL POD AUTOSCALER (HPA) & METRICS SERVER
* **📊 Metrics Server:** Collects resource metrics (CPU/Memory) from Kubelets across the cluster so autoscalers can read them.

### 🔑 Step-by-Step Metrics Server Installation & Configuration (Certificate Fix)
* **Step 1:** Download the official metrics-server manifest:
  `wget -O metricserver.yml https://github.com/kubernetes-sigs/metrics-server/releases/latest/download/components.yaml`
* **Step 2:** Open `metricserver.yml` and locate the `Deployment` object. Inside the container arguments (`args`), add `--kubelet-insecure-tls` to bypass self-signed certificate errors in development/Minikube environments:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: metrics-server
  namespace: kube-system
spec:
  template:
    spec:
      containers:
      - name: metrics-server
        image: registry.k8s.io/metrics-server/metrics-server:v0.6.4
        args:
          - --cert-dir=/tmp
          - --secure-port=4443
          - --kubelet-insecure-tls   # 🛠️ <-- ADD THIS LINE HERE TO AVOID CERTIFICATE ERRORS
          - --metric-resolution=15s

* **Step 3:** Apply the modified manifest to your cluster:
  `kubectl apply -f metricserver.yml`

## 4. ⚙️ KUBERNETES JOBS
* **📌 Definition:** A Job creates one or more Pods and ensures a specified number of them successfully terminate (exit code 0).
* **🔄 Why it's used normally:** Unlike Deployments (which run continuously like web servers), Jobs run to completion and then stop.
* **⚖️ Difference from other objects:** Deployments/ReplicaSets keep running services forever; Jobs run finite tasks and stop.
* **💼 Use Cases:** Log rotation, scheduled interval tasks, batch processing, Helm chart DB migrations, and database backups.

### 📄 Manifest (`job.yml`)
apiVersion: batch/v1
kind: Job
metadata:
  name: testjob # 🏷️ Name of the Job object
spec:
  template:
    metadata:
      name: testjob
    spec:
      containers:
        - name: counter
          image: centos:7
          command: ["bin/bash", "-c", "echo Technical-Guftgu; sleep 5"] # ⏱️ Finite task command execution
      restartPolicy: Never # 🔒 Required for Jobs (Prevents infinite restart loops on successful exit)

### 🛠️ Commands Executed & Output Logs:
# 1. Check current pods
kubectl get pods
# -> Expected Output:
# No resources found in default namespace.

# 2. Clean up any previous job and apply the new one
kubectl delete -f job.yml --ignore-not-found=true
kubectl apply -f job.yml
# -> Expected Output:
# job.batch/testjob created

# 3. Watch the pods run and complete
watch kubectl get pods

## 6. 🕒 KUBERNETES CRONJOBS

apiVersion: batch/v1beta1
kind: CronJob
metadata:
   name: bhupi
spec:
  schedule: "* * * * *" # ⏱️ Cron syntax: Triggers a new job execution every single minute

    spec:
      template:

## 7. 📥 INIT CONTAINERS
* **📌 Definition:** An Init Container is a specialized container that runs to completion **before** your main application containers start up inside a Pod. They always run sequentially one after another.
* **💼 Use Cases (Detailed):**
  1. **Seeding a Database:** Populating initial tables or default configuration data into a database before backend start.
  2. **Waiting for Dependencies:** Blocking application startup until a dependent service is reachable over network.
  3. **Cloning a Git Repository:** Pulling source code files from remote Git repos into shared storage volumes.
  4. **Generating Config Files Dynamically:** Constructing configuration files on the fly using environment variables.

### 📐 Init Container Flow Diagram
[ Pod Starts ] 
      ▼
 ┌────────────────────────────────────────┐
 │ Init Container 1: Wait for DB          │ ──(Runs to completion: SUCCESS)
 └────────────────────────────────────────┘
      ▼
 ┌────────────────────────────────────────┐
 │ Init Container 2: Clone Git Repo       │ ──(Runs to completion: SUCCESS)
 └────────────────────────────────────────┘
      ▼ (All init containers passed!)
 ┌────────────────────────────────────────┐
 │ Main Application Container (Running)   │ ──(Starts serving traffic)
 └────────────────────────────────────────┘

### 📄 Manifest (`init.yml`)
apiVersion: v1
kind: Pod
metadata:
  name: initcontainer-pod
spec:
  initContainers:
    - name: init-myservice
      image: busybox:1.28
      command: ['sh', '-c', 'echo "Initializing..."; sleep 5'] # 🔄 Must finish successfully before main-app starts
  containers:
    - name: main-app
      image: centos
      command: ["/bin/bash", "-c", "while true; do echo App running; sleep 5; done"]

### 🛠️ Commands Executed & Output Logs:
# 1. Apply init container pod
kubectl apply -f init.yml
# -> Expected Output:
# pod/initcontainer-pod created

# 2. Watch pod status change from Init to Running
watch kubectl get pods

# 3. Check logs of the init container
kubectl logs -f pod/initcontainer-pod -c init-myservice
# -> Expected Output:
# Initializing...
